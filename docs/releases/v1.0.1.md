# FHOPS v1.0.1

## Summary

FHOPS 1.0.1 is a maintenance release on the stable 1.0 line (Phase 8, parent issue #90), built from
`v1.0.0`. It fixes defects found while the FHOPS SoftwareX manuscript was revised
(UBC-FRESH/fhops-manuscript#20) and during two audits of the release before publication. Every
comparison in these notes is with **v1.0.0**.

**Is it a patch release?** It is numbered 1.0.1 because it stays on the 1.0 line. It also adds
optional fields and API, so strict SemVer would call it 1.1.0. Many fixes change results, so
treat the upgrade as a behaviour change.

**Headline behaviour changes**

- **Rolling horizon** now carries state between windows (remaining volume, staged inventory, role
  progress, machine positions, user locks, blackouts). v1.0.0 re-planned every block from scratch
  in each window. Rolling results change completely.
- **Stochastic playback** events were re-implemented (per-landing-day shocks, sampled downtime
  durations, composing events). Results differ for the same seed.
- **Operational MILP formulation** was corrected (role output capped at block volume, per-upstream
  staged inventories, partial last truckload, landing capacity per shift slot, moves charged as in
  the KPIs, locks and timeline blackouts enforced, unsequenced blocks). Objectives and plans change;
  for example, the tiny7 optimum is 279.796036 (v1.0.0: 4388.082752) because its capacity-1
  landings now bind.
- **SA, ILS and Tabu** report the exact objective of the schedule they return (v1.0.0 could
  overstate it when mobilisation or transitions were weighted) and keep every shift within a hard
  landing capacity. Objectives and plans change.
- **Validation is stricter** and happens when the scenario is loaded. Run `fhops validate` on your
  scenarios.
- **`fhops solve-mip` is deprecated** and now solves the operational MILP; its console output
  changed. The legacy day-level MIP behind it is infeasible for every scenario whose harvest
  system has a loader role.
- **MILP APIs no longer raise** for infeasible models, time limits without an incumbent, or solver
  failures: they return an `outcome` (`optimal`, `feasible`, `infeasible`, `no_solution`,
  `error`).

**Who must re-run what:** see the [upgrade checklist](#upgrade-checklist).

**The tactical layer is not here.** The tactical–operational planning layer is on the separate
1.1.0 alpha line (`fhops==1.1.0a1`, released 2026-09-28). **1.1.0a1 contains none of the fixes
in this release.** Because 1.1.0a1 has the higher version number, `pip install --pre fhops`
installs it, not 1.0.1.

## Installation

```bash
pip install fhops==1.0.1

# Development / verification (from a source checkout)

```

Requires Python ≥ 3.11 (unchanged). Minimum versions of several dependencies were raised; see
[Dependencies and packaging](#dependencies-and-packaging).

## Upgrade checklist

1. **Validate your scenarios:** `fhops validate path/to/scenario.yaml`. Inputs that 1.0.1 rejects
   are listed under [Scenario contract and validation](#scenario-contract-and-validation). The
   most likely new failures are:
   - blocks whose `harvest_system_id` is not registered;
   - locks outside the block's `earliest_start`/`latest_finish` window;
   - locks on machines whose role is not in the block's harvest system.
2. **Re-run studies, by type:**

   | Study type | Re-run? | Why |
   |---|---|---|
   | Rolling horizon (`fhops plan rolling`, `solve_rolling_plan`) | Always | State carry-forward, locks, blackouts, MILP earliness tie-break |
   | Stochastic playback (`fhops eval-playback --samples …`, `run_stochastic_playback`) | Always | Event semantics changed |
   | Operational MILP (`solve-mip-operational`, `bench suite --include-mip`, `benchmark`, ILS `--hybrid-use-mip`) | Always | Formulation corrections |
   | `fhops solve-mip` / `solve_mip` | Always | Now solves the operational MILP, not the legacy MIP |
   | SA / ILS / Tabu | Always | Exact objective, landing capacity, penalty, multi-shift repair |
   | Deterministic playback / `fhops evaluate` of an existing assignment table | If the scenario has several shifts per day, head starts, or the table is empty | Shift-slot semantics, shift hours, empty-plan KPIs (see [Playback and KPIs](#playback-and-kpis)) |
   | `fhops dataset` productivity / costing | Only with `--partial-cut-profile sr109_green_tree` cost output, or if v1.0.0 commands failed with Typer ≥ 0.26 | [Data corrections](#data-corrections), [CLI](#cli) |

3. **File compatibility.** `schema_version` stays `1.0.0`; all new fields are optional.
   - Scenario files that use `initial_state`, `locked_assignments[].shift_id`, or
     `locked_assignments[].production` need `fhops>=1.0.1`. v1.0.0 does not reject them. It
     silently ignores `initial_state` and `production`, and reads a shift lock as a whole-day lock.
   - Assignment CSVs for scenarios with more than one shift per day must have a `shift_id` column.
     v1.0.0 replayed such rows as `S1`; 1.0.1 rejects them.
4. **Scripts that parse FHOPS output** must be checked:
   - `fhops solve-mip` and `fhops solve-mip-operational` print a new result line.
   - The rolling-horizon CSV has a new `shift_id` column, which shifts the column positions.
   - Rolling JSON/CSV summaries have new keys.
   - `fhops bench suite` adds summary columns.
   - Several CLI exit codes changed.

   See [CLI](#cli) and [Rolling horizon](#rolling-horizon).
5. **Replace deprecated entry points** (see [Deprecations](#deprecations)):
   - use `fhops solve-mip-operational` instead of `fhops solve-mip`;
   - use `fhops.model.milp.driver.solve_operational_milp` instead of
     `fhops.optimization.mip.solve_mip`.

   Remove `correlated_days` and `seed_offset` from stochastic configs.
6. **Pin `fhops==1.0.1`** (or `>=1.0.1,<1.1`) if you need these fixes. Do not install
   `fhops==1.1.0a1` or use `pip install --pre`.

## Changes by area

### Scenario contract and validation

New and changed contract (#91, #109, #118, #125):

- **`Scenario.initial_state`** (optional, `ScenarioInitialState`) describes the state at the start
  of the horizon:
  - `BlockInitialState`: `role_remaining`, `staged_inventory`, `role_shift_counts`;
  - `MachineInitialState`: `last_block_id`.

  It is honoured by the operational MILP, the heuristics and playback. `None` (default) starts from
  the v1.0.0 initial conditions. Leaving it unset does not undo the other changes in this release.
  `role_shift_counts` is informational: head starts are enforced as staged volume (#109). New public
  API: `validate_initial_state`, which is exported from `fhops.scenario.contract` together with the
  new models, and `fhops.scenario.contract.models.ROLE_REMAINING_TOLERANCE` (1e-6 m³).
- **`ScheduleLock.shift_id`** (optional): `None` locks every shift of the day in which the machine
  is available; a label locks one `(day, shift)` slot. A blank label is rejected.
- **`ScheduleLock.production`** (optional, m³ ≥ 0): the planned production of a locked slot.
  Solvers ignore it. Rolling-horizon carry-forward and `compute_rolling_kpis` use it, so a stitched
  MILP plan replays the production the MILP chose. If a day-level lock (`shift_id` unset) carries
  `production` and the machine has several available shifts that day, the lock is ambiguous and
  rolling replay and export reject it (#125).
- **`Scenario.shift_labels()`** (new method) returns the labels accepted for
  `ScheduleLock.shift_id`:
  - the `shift_calendar` labels when a shift calendar exists;
  - otherwise the timeline shift names;
  - otherwise `{"S1"}`.
- **`Landing.daily_capacity`** is now applied per shift slot `(day, shift)` by both the MILP and
  the heuristics. It is a hard limit when `ObjectiveWeights.landing_surplus` is 0 (the default).
  Otherwise the `k`-th machine beyond capacity in a slot costs `k × landing_surplus`. The field
  name is unchanged.
- `Block.work_required` and `ProductionRate.rate` are documented consistently in m³: terminal
  delivered volume, and volume per shift assignment (#94). This is a documentation-only change.

Validation (#100, #118, #129):

- **When validation runs (#100).** `load_scenario` now cross-validates the whole scenario once all
  optional YAML sections are attached, so every CLI command and every Python caller sees errors
  at load. These sections are locks, timeline, mobilisation, crew assignments, harvest systems,
  and initial state.
  - v1.0.0 attached these sections without the scenario cross-checks.
  - v1.0.0 commands that build a `Problem` still applied the checks v1.0.0 already had: the
    solvers, `evaluate`, `eval-playback` and `validate`. Those commands failed later, with a
    `validation error for Problem`.
  - In v1.0.0, `fhops plan rolling` and Python code using the loaded `Scenario` directly skipped
    the checks. `plan rolling` also silently dropped user locks.

  The checks v1.0.0 already had, now applied at load, reject:
  - locks with unknown machines or blocks, days outside the horizon, duplicates, or on
    blackout days;
  - crew assignments with unknown machines or duplicate `crew_id`;
  - mobilisation parameters for unknown machines;
  - distance tables that name blocks outside the scenario (trim distance CSVs that cover more
    blocks than the scenario).
- **New checks** (for YAML and Python-built scenarios; rejected in every entry point):
  - lock `shift_id` must be a known label (see `shift_labels()`);
  - a machine/day cannot have both a day lock and shift locks, or duplicate shift locks;
  - locks outside the block's `[earliest_start, latest_finish]` window;
  - locks on a block with `harvest_system_id` whose machine has no role or a role outside that
    system;
  - invalid `initial_state` entries: unknown ids, roles outside the block's system, role-keyed
    state on a block without `harvest_system_id`, negative values, or `role_remaining` above
    `work_required` + 1e-6 m³;
  - `ScheduleLock.production < 0`.
- **Unknown `harvest_system_id` rejected (#129).** A block's `harvest_system_id` must be defined
  in `Scenario.harvest_systems` or in `fhops.scheduling.systems.default_system_registry()`
  (scenario systems are overlaid on the registry).
  - v1.0.0 had this check, but it never ran. Such blocks loaded, and the solvers disagreed: the
    operational MILP could not harvest the block, while the heuristics and playback delivered it
    without sequencing.
  - To fix an affected file, define the system under `harvest_systems` or use a registry id.
  - All scenarios bundled in this repository and the nine BC case-study scenarios used during
    development load unchanged. The only exception is the repository's own regression fixture
    `tests/fixtures/regression/regression.yaml`, which now defines its custom system.
- Details: `docs/howto/data_contract.rst` ("Compatibility with FHOPS 1.0.0").

### Operational MILP

All changes affect `fhops solve-mip-operational` and `solve_operational_milp`. Since #127 they also
affect `fhops solve-mip`, `fhops benchmark`, `fhops bench suite --include-mip`, the ILS hybrid step
and rolling MILP windows. The formulation's "Changes from FHOPS v1.0.0" paragraph in
`docs/howto/optimization_formulation.rst` lists every equation change.

**Physical feasibility and agreement with playback (#109, #110, #115)**

- Every role's output is capped at the block's remaining volume. v1.0.0 let upstream roles
  process more wood than the block holds and used it to meet buffers.
- The head-start buffer is waived once the upstream roles have finished the block.
- The loader threshold is `min(truckload, volume still to deliver)`, so a block's last partial
  truckload can be loaded.
- Staged inventory is kept per upstream role. For joins, each upstream role must have handled
  the wood; v1.0.0 pooled the outputs of all upstream roles.
- Blocks without `harvest_system_id` have no role obligations, as documented in the data contract.
  v1.0.0 applied the registry's default system to them.
- Timeline blackouts are enforced in every slot of a blackout day for every machine. v1.0.0
  enforced them only in the heuristics.
- Result: a feasible MILP plan replays under playback with zero sequencing violations, and
  playback delivers the MILP's terminal production. This was checked on random harvest-system
  graphs (`tests/sequencing/`).

**Landing capacity (#125).** v1.0.0 counted machine-shifts per landing per day and added a slack
variable that was free at the default `landing_surplus = 0`, so the capacity never bound. The
MILP now applies the heuristics' rule per shift slot: a hard limit at weight 0, otherwise
`k × landing_surplus` for the `k`-th extra machine.

- If locks alone exceed a hard capacity in a slot, the locked machines are kept, no other machine
  may join, and a warning is issued; the model does not become infeasible.
- Heuristic incumbents that overload a landing are no longer accepted as MIP starts.
- MILP results change wherever landings bind. For example, the tiny7 optimum is 279.796036
  (v1.0.0: 4388.082752) because its landings have capacity 1.

**Moves charged like the heuristics and KPIs (#139).**

- v1.0.0 charged `ω_trans` whenever a machine worked two consecutive slots, even on the same
  block. It also linked only consecutive slots, so a move across an idle slot was free.
- Each machine's position is now modelled as a unit flow through a position network (continuous
  arcs; exact for binary assignments). A move is charged whenever a machine works a block other
  than its last worked block or its carried-in `initial_state` block.
- Code that read the MILP variables `y`, `loads` or `loader_partial` must switch to the position
  network: `stay`, `y` or `depart`/`arrive`, `first`, `unplaced`.
- The integer loader-batching variables were removed; they constrained nothing.
- The model is smaller than in v1.0.0. tiny7 has 976 constraints and 152 binary/integer
  variables (v1.0.0: 1119 and 370); small21 has 7626 and 1376 (v1.0.0: 23289 and 7866).
- With landing capacities that cannot bind, tiny7's optimum is 4361.462752 instead of v1.0.0's
  4388.082752: the v1.0.0 optimum hid one move across an idle day.

**Locks and initial state (#91, #115).**

- `Scenario.locked_assignments` are enforced (the v1.0.0 operational builder ignored them).
  Locked machines may stay idle, so locks never make the model infeasible.
- Contradictory locks are pinned to idle with a warning. These are locks outside the block window
  or with an incompatible role, which validation normally rejects first.
- `initial_state` sets:
  - the first-slot staged inventory and head start;
  - per-role remaining output;
  - the machine's starting position.

**Earliness tie-break (#141).** `solve_operational_milp(earliness=True)` and
`fhops solve-mip-operational --earliness` add a second, lexicographic solve. It maximises
production-weighted earliness while keeping the base objective within a relative 10⁻⁶ of the
first solve.

- The reported `objective` remains the base objective. The result gains an `earliness` dict.
- The option is off by default for standalone solves and on by default for rolling-horizon MILP
  windows.

**Results API (#99, #115, #139).** `solve_operational_milp` no longer raises for infeasible models,
time limits without an incumbent, or solver failures. This includes solver-interface exceptions
such as `gurobipy.GurobiError` for a missing or size-limited licence.

- New result keys: `has_solution`, `outcome` (`optimal|feasible|infeasible|no_solution|error`),
  `solver_error`, `warnings`, `warm_start`, `solver`, and `earliness`.
- Without a solution, `objective` is `None` and the assignment table is empty but keeps its
  columns.
- A solve stopped by a time or iteration limit returns its best incumbent. v1.0.0 returned
  `objective=None`.
- Exported production is clamped at 0.
- The new `OperationalMilpBundle` fields (locks, initial state, blackout slots, unsequenced blocks)
  are serialised only when present.

### Heuristics (SA, ILS, Tabu)

- **Exact objective (#131).** In v1.0.0 a candidate's score could omit the mobilisation and
  transition costs of machines the repair pass had not touched. The reported `objective` could
  therefore exceed a fresh evaluation of the returned schedule.
  - Example from the SoftwareX benchmark assets committed for v1.0.0: tiny7 SA and ILS were
    overstated by 10.748. Audits of the same committed assets found overstatements of 54–151 on
    small21 and up to about 3089 on med42 (SA and ILS).
  - Now `objective`, `meta["best_score"]`, telemetry and watch snapshots equal a fresh
    evaluation of the exported assignments.
  - Delivered volume and the mobilisation KPIs computed from the assignments were not affected
    in v1.0.0.
  - Example pinned in the tests: tiny7 SA with 300 iterations and seed 123. v1.0.0 reported
    4306.522752 for a plan whose true score is 4295.774752; 1.0.1 returns a different plan
    scoring 4338.516752.
- **Landing capacity (#116, #140).** With a hard landing capacity (`landing_surplus` weighted 0,
  the default), the repair keeps every shift slot within `Landing.daily_capacity` on every day.
  A capacity-0 landing admits no machine.
  - A machine whose input is staged keeps a place on its landing ahead of upstream roles, so
    downstream roles are never starved.
  - Heuristic plans therefore no longer overload landings that the MILP forbids, and they are
    valid MILP warm starts.
  - On capacity-limited scenarios, delivered volume can be lower than in v1.0.0, because v1.0.0
    bought volume with landing overloads.
  - Example (BC case study `ka_6`, 3 shifts per day, SA 1500 iterations, seeds 1–3): v1.0.0
    reported 24913.36 / 23913.36 / 22913.36; 1.0.1 reports 30913.36 for each seed, with full
    delivery and no overloads.
- **Hard-violation penalty (#140).** Each hard violation now costs
  `max(1000, 2·ω_prod·r_max + ω_mob·c_max + 1)` instead of a flat 1000
  (`OperationalProblem.hard_violation_penalty()`). Hard violations are an unavailable slot, a
  broken lock, a wrong role, a slot outside the block window, a missing rate, a sequencing
  violation, and a hard landing overload. Idle unavailable slots are no longer charged (#131):
  v1.0.0 added 1000 per unavailable machine-slot, a constant offset that did not change which
  plan wins.
- **Sequencing (#109, #116).** Staged output is released per shift slot instead of per day. The
  head-start waiver uses upstream output from before the current slot. Head starts are measured
  in staged volume. Locked slots stay on their block.
- **Automatic weight overrides made visible (#140).** The heuristics search the scenarios named
  "FHOPS Tiny7" and "FHOPS Small21" with built-in objective weights:
  production 1.0, mobilisation 0.2, transitions 0.1, soft landing capacity 0.05
  (`AUTO_OBJECTIVE_WEIGHT_OVERRIDES`). The MILP uses the scenario weights instead.
  - This behaviour is unchanged from v1.0.0 but is now recorded in `meta`
    (`objective_weight_overrides`, `objective_weight_overrides_source`,
    `scenario_objective_weights`) and in telemetry.
  - `solve-heur`, `solve-ils`, `solve-tabu`, `benchmark` and `bench suite` print a one-line notice.
- **ILS hybrid step (#104, #127, #140).** `solve_ils(..., hybrid_use_mip=True)` and
  `solve-ils --hybrid-use-mip` now solve the operational MILP (HiGHS), using the best ILS schedule
  as the MIP start. The ILS keeps the MILP plan only if it scores higher.
  - In v1.0.0 this step solved the legacy MIP, which is infeasible for loader systems, so it
    never changed the schedule.
  - `meta["hybrid_mip"]` records each solve.
- **New API:**
  - `evaluate_assignments` scores an assignment table as planned, without repair, using a
    `production` column when present;
  - `schedule_from_assignments`, `rescore_fresh` and `fresh_schedule_copy`;
  - `objective_weight_override_source`, `record_objective_weight_overrides` and
    `objective_weight_override_notice` (all in `fhops.optimization.heuristics.common`);
  - `OperationalProblem.hard_violation_penalty()` and `lock_for()`.
- `use_local_repairs=True` (Python API only) is documented as an approximate search mode. Its
  reported objective is still exact.

### Rolling horizon

**State carry-forward (#92).** After each window, the stitched locked plan is replayed on the base
scenario with the playback sequencing tracker. The next window then starts from the resulting
state:

- remaining block volume (finished blocks stay finished);
- per-role remaining output, staged inventory and shift counts;
- each machine's last block.

User locks are merged into every window, blackouts are rebased into window coordinates, and
locks keep `shift_id` and the MILP's planned `production`. `compute_rolling_kpis` uses the same
replay, so the carried state and the reported KPIs agree. New public API: `carry_forward_state`,
`RollingCarryState`, `slice_scenario_for_window(..., carry_state=)`, and `MILPSolver` exported
from `fhops.planning`.

**MILP backend.** `--mip-solver auto`, the default, now works: it uses Gurobi when available and
falls back to HiGHS, the same rule as `solve-mip-operational --solver auto`. In v1.0.0,
`fhops plan rolling --solver mip` with the default `auto` failed because Pyomo has no solver named
`auto`.

**Windows without a solution (#117).** Such a window is recorded with `status="no_solution"`.
Nothing is locked for its lock span, and the run continues.

- Windows with nothing to plan are `status="skipped"`. v1.0.0 raised an error for some of these.
- Day-level locks are expanded to the machine's available shifts (#125).
- Locks outside their block's window are rejected before any window is solved.
- A partial `shift_calendar` no longer falls back to `S1` inside a window.

**Earliness tie-break (#141).** The MILP objective does not depend on *when* work is done inside a
window, so a window could defer its work beyond its lock span. MILP windows now run the
lexicographic earliness stage by default (`--mip-earliness/--no-mip-earliness`,
`--mip-earliness-time-limit`).

- A window can take up to about twice `--mip-time-limit`.
- Windows whose lock span covers the whole window skip the stage.

**CLI flags and exit codes (#117, #141).**

- `--fail-on-empty-window` stops at windows without a solution **and** at empty windows.
- `--fail-on-no-solution` stops only at windows without a solution.
- `--max-iterations` must be ≥ 1.
- Exit 1 when a `--fail-on-*` flag stops the run, the run fails, or no window returns a solution.
  Partial outputs are always written, and `--out-json` gets an `error` key.
- Exit 2, without a traceback, for invalid horizon arguments or an unavailable `--mip-solver`.
- In v1.0.0, `RollingInfeasibleError` was reported as a usage error (exit 2).
- `fail_on_empty_window` and `fail_on_no_solution` parameters were added to `run_rolling_horizon`
  and `solve_rolling_plan`. `RollingInfeasibleError` carries `iteration_index` and
  `partial_result`.

**Output format changes (check your parsers).**

- **`--out-assignments` / `rolling_assignments_dataframe`:**
  - a `shift_id` column is inserted after `day`
    (`machine_id, block_id, day, shift_id, assigned[, production][, metadata…]`);
  - MILP runs add `production`;
  - rows are sorted by `day, shift_id, machine_id, block_id`;
  - new optional keyword `scenario=` expands day-level locks.
- **Summary JSON (`--out-json`, `summarize_plan`)** gains top-level `empty_windows`,
  `no_solution_windows`, `skipped_windows`, `empty_window_indices` and
  `no_solution_window_indices`.
- **Each iteration record** (also `--out-iterations-jsonl/-csv`) gains `remaining_work_start`,
  `status`, `has_solution`, `planned_delivered`, `locked_delivered`, `locked_production`,
  `empty` and `error`.
- **Run metadata** gains `fail_on_empty_window`, `fail_on_no_solution` and, for MILP runs,
  `mip_earliness` (plus `mip_earliness_time_limit` when set).
- **`RollingIterationSummary`** and `SolverOutput` gain the matching fields (`SolverOutput`:
  `has_solution`, `error`). `RollingPlanResult` gains `empty_windows` and `no_solution_windows`.
- **`evaluate_rolling_plan`** metadata gains the window counts.
- **Empty baseline (#108):** an explicitly supplied empty baseline is scored as a zero-delivery
  plan instead of being dropped.

### Playback and KPIs

- **Empty plans (#108).** `compute_kpis` reported full delivery for an empty assignment table, for
  example a MILP run that found no solution. It now reports 0 delivered and the full remaining
  work. KPIs of non-empty plans are unaffected by this fix.
- **Multi-shift scenarios (#109, #116).**
  - Staged output is released per shift slot, in one chronological slot order (day, then
    timeline definition order).
  - Rows without `shift_id` raise an error in playback, KPIs, stochastic playback,
    `fhops evaluate` and `fhops eval-playback` (exit 1 with a message) whenever some day has more
    than one shift. v1.0.0 replayed them all as `S1`.
  - Without a timeline shift definition, a shift's hours are the machine's `daily_hours` divided
    by its number of shifts that day. v1.0.0 recorded the full `daily_hours` per shift. This
    affects hours, utilisation and the downtime fraction.
- **Sequencing semantics (#109, #125).**
  - Head starts are measured in staged volume.
  - The loader truckload rule uses the volume staged at the start of the slot.
  - The volume tolerance is 1e-6 m³ (`SEQUENCING_TOLERANCE`).
  - An assignment with planned production 0 is idle, so it no longer counts as `missing_prereq`.

  Deterministic playback of the bundled single-shift v1.0.0 plans (tiny7, med42) is unchanged.
  Plans that rely on head starts, loaders at block tails, or several shifts per day can replay
  differently.
- **Stochastic playback (#93, #116).**
  - Landing shocks start per landing and day and last `duration_days` calendar days. v1.0.0
    sampled once per landing and counted down per assignment row.
  - Downtime removes a sampled duration (`mean_duration_hours`/`std_duration_hours`, defaults
    4 h / 1.5 h, clipped to the shift) instead of the whole shift. Downtime-hour KPIs now report
    the sampled hours; in v1.0.0 they were always 0.
  - Weather and landing effects compose with earlier events instead of overwriting them.
  - Events ignore the DataFrame index; duplicate index labels corrupted results in v1.0.0.
  - `downtime_production_loss_est`, `weather_production_loss_est` and `weather_hours_est` are
    sums of what the events removed. v1.0.0 multiplied hours by an all-role average rate.
  - New `eval-playback` options: `--downtime-mean` and `--downtime-std`.
- **New API:**
  - `PlaybackRecord.downtime_hours`;
  - `LandingShockEvent.sample_multipliers()`;
  - in `fhops.evaluation.playback`: `adapters.normalise_shift_ids`, `adapters.multi_shift_days`
    and `core.shift_hours_resolver`;
  - `fhops.evaluation.sequencing.SEQUENCING_TOLERANCE`.

  The internal, unexported TypedDict `stochastic.LandingShockState` was removed.

### Warm start and solver handling

- **HiGHS warm starts work (#99).** With current Pyomo (for example 6.10), `--incumbent` /
  `incumbent_assignments=` raised a `TypeError` for HiGHS. Seeded HiGHS solves now use APPSI HiGHS
  MIP starts.
  - The CLI, the result (`warm_start`) and telemetry report whether HiGHS accepted the start.
    Acceptance is inferred when the HiGHS log gives no verdict (#115).
  - Solvers without MIP-start support run without the start and emit `MilpWarmStartWarning`.
- **`solver="auto"` (#139).** `solve_operational_milp(solver="auto")` and
  `solve-mip-operational --solver auto` use Gurobi when it is available, otherwise HiGHS.
  - After a Gurobi failure, such as a missing or size-limited licence, they retry with HiGHS and
    emit `MilpSolverFallbackWarning` plus a `warnings` entry.
  - `solve_mip(driver="auto")` and `fhops solve-mip --driver auto` behave the same way.
  - The default solver remains `highs`.
- The gap option is no longer sent as `mip_rel_gap` to `appsi_gurobi` and `gurobi_direct`.
- The HiGHS `ERROR` log lines and solver exceptions are reported as `solver_error`, not as
  infeasibility.

### CLI

**`fhops solve-mip`, deprecated alias (#124, #127).**

- It prints a `Deprecated:` notice and a Python `LegacyMipDeprecationWarning`, then solves the
  operational MILP.
- Driver mapping:
  - `auto` → Gurobi when installed, otherwise HiGHS, and HiGHS after a Gurobi error;
  - `highs-appsi` / `highs-exec` → HiGHS;
  - `gurobi` / `gurobi-appsi` / `gurobi-direct` → `gurobi` / `appsi_gurobi` / `gurobi_direct`.

  `MIP outcome=<outcome> solver_status=… termination=… objective=<value>|n/a`, then
  `Assignments written to <out>`, solver errors and warnings.

  - 0 when the solver ran (including infeasible models and no incumbent);
  - 1 on a solver error or unavailable solver;

  On the bundled examples v1.0.0 exited with a traceback because the legacy MIP is infeasible.

  objective=…|n/a` (v1.0.0: no `outcome=`).

**`fhops benchmark` (#124, #127, #140).**

## Deprecations

All deprecated items still work in 1.0.1 and will be removed in a future release.

| Deprecated | Replacement | Warning |
|---|---|---|
| `fhops solve-mip` | `fhops solve-mip-operational` | `Deprecated:` notice + `LegacyMipDeprecationWarning` |
| `fhops build-mip` | `fhops solve-mip-operational`; for model sizes, `build_operational_model` (Python) | `Deprecated:` notice |
| `fhops.optimization.mip.solve_mip` | `fhops.model.milp.driver.solve_operational_milp` | `LegacyMipDeprecationWarning` (a `DeprecationWarning`) |
| `fhops.optimization.mip.builder.build_model` (legacy day-level MIP) | `fhops.model.milp.operational.build_operational_model` | `LegacyMipDeprecationWarning` |
| `WeatherEventConfig.correlated_days` (never had an effect) | `impact_window_days` | `DeprecationWarning` when set to a non-default value |
| `seed_offset` on stochastic event configs (never had an effect) | none (samples use `base_seed + sample_id`) | `DeprecationWarning` when set to a non-default value |

`solve_mip` keeps the v1.0.0 keys `objective` and `assignments`. It adds `has_solution`, `outcome`,
`solver_status`, `termination_condition`, `solver_error`, `warnings`, `production`, `warm_start`
and `solver`. It raises only `SolverUnavailable` (missing solver) or `ValueError` (unknown driver).
Its objectives are operational-MILP objectives, so they cannot be compared with v1.0.0 legacy-MIP
values. The `correlated_days` and `seed_offset` warnings are attributed to the caller's line, so
Python's default warning filters show them in scripts.

## Known limitations

- **MILP solve times.**
  - Large and multi-shift scenarios can be slow to solve. Without a warm start, HiGHS may not
    find a useful incumbent within practical time limits. For example, in development runs med42
    returned only the empty plan at 120 s, and 3-shift BC case studies needed far longer unseeded
    than when seeded with an SA plan.
  - Seed such runs with a heuristic plan (`--incumbent`). Heuristic plans are valid starts when
    they respect landing capacity.
  - Time limits cover only the solver. Building the Pyomo model, which takes several seconds on
    large scenarios, is not counted.
  - The earliness stage can double the solve time per rolling window.
  - The corrected model takes longer to prove optimality on some small instances, because moves
    the old model let it avoid now have a cost.
- **Fork/join semantics.** Roles fed by one upstream role split its staged volume. A join needs
  the output of every upstream role. A fork that joins again (a diamond) can deliver at most half
  of the block. For a join, the head-start buffer computed from the summed upstream rates is
  required of each upstream role. MILP and playback agree on these rules, but they may not match
  every field operation.
- **Rolling horizon.** Windows assign no value to work in progress at the window end, so very
  short windows relative to the harvest-system chain can under-plan upstream work. MILP windows
  can lock assigned-but-idle slots after the work is done; this does not affect KPIs or replay.
- **Heuristic weight overrides** apply to any scenario named "FHOPS Tiny7" or "FHOPS Small21".
  Compare heuristic and MILP objectives only under the same weights
  (`objective_scenario_weights`, `evaluate_assignments`).
- **Reproducibility of seeded heuristics.** Seeded heuristic runs are reproducible on a fixed
  platform (verified bit-for-bit for SA). Last-bit floating-point differences between numpy/Python builds can change an
  acceptance decision and therefore the trajectory. Published values are reproducible on the
  documented platform, not bit-for-bit everywhere.
- **Legacy MIP retired.**
  - The legacy day-level MIP (`fhops.optimization.mip.builder.build_model`) is infeasible for
    every scenario whose harvest system has a loader role with machines: its loader-buffer
    constraint demands a negative buffer in the first shift. This was already true in v1.0.0.
  - The builder remains importable but deprecated, and no FHOPS solver uses it.
  - The operational MILP, the formulation documented in the FHOPS paper, is not affected.
