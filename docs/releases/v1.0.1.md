# FHOPS v1.0.1

## Summary
- Maintenance release on the stable 1.0 line (Phase 8, parent issue #90), cut from `v1.0.0`.
- Fixes defects found during the SoftwareX R2 review of the FHOPS manuscript
  (UBC-FRESH/fhops-manuscript#20): rolling-horizon state carry-forward, stochastic playback
  event semantics, MILP warm start with HiGHS, and lock validation.
- Adds one optional scenario-contract section (`Scenario.initial_state`) and an optional
  `ScheduleLock.shift_id`. Scenarios without them start from the same initial conditions as in
  v1.0.0, but results can still change where this release fixes behaviour (marked "behaviour
  change" below). Scenario files that use the new fields require `fhops>=1.0.1`: v1.0.0 silently
  ignores `initial_state` and reads shift locks as whole-day locks (`schema_version` stays `1.0.0`).
- Validation is stricter: some inputs v1.0.0 accepted are now rejected when the scenario is loaded
  (see "Scenario validation and compatibility" below).
- The tactical–operational planning layer remains on the separate 1.1.0 alpha line
  (`pip install --pre fhops==1.1.0a1`) and is not part of this release.

## Installation
```bash
pip install fhops==1.0.1

# Development / verification
pip install hatch
hatch run dev:suite
```

## Fixes and changes

### Rolling-horizon planning (#92) — behaviour change
In v1.0.0 the rolling-horizon driver (`fhops plan rolling`, `fhops.planning.solve_rolling_plan`)
carried no state between windows, contrary to its design notes:
- every window re-planned each block's full `work_required`, including blocks finished in earlier
  locked days;
- staged inter-role inventory, role progress, and head-start counts restarted at zero;
- machines had no starting position, so moves at window boundaries were free inside the solve;
- user `Scenario.locked_assignments` were dropped;
- blackout timelines were not rebased into window coordinates;
- locks lost their `shift_id`.

v1.0.1 replays the stitched locked plan after each window against the base scenario (the same
sequencing-tracker path playback uses) and carries the resulting state into the next window:
remaining block volume (`work_required`; finished blocks stay at 0), per-role remaining output,
staged inventory and shift counts, and each machine's last block (`Scenario.initial_state`). User
locks are merged into every window, blackouts are rebased into window coordinates, locks keep
`shift_id`, and MILP locks carry the production the MILP planned so the replay executes the plan
the solver chose. Stitched-plan KPIs (`compute_rolling_kpis`) use the same replay, so carried
state and reported KPIs agree. Hooks record runtime; `solver="auto"` resolves to HiGHS.
**Rolling-horizon results from v1.0.0 and earlier should be re-run.** Known limitation: windows
assign no value to work-in-progress left at the window end, so very short windows relative to the
harvest-system chain can under-plan upstream work.

### Scenario contract (#91)
- New optional `Scenario.initial_state` (`BlockInitialState`: `role_remaining`, `staged_inventory`,
  `role_shift_counts`; `MachineInitialState`: `last_block_id`), honoured by the operational MILP
  (first-slot staged inventory and head-start, per-role remaining cap, boundary move cost), the
  heuristics, and playback.
- New optional `ScheduleLock.shift_id` (`None` = whole day). The operational MILP now enforces
  `Scenario.locked_assignments` (previously ignored by that builder).
- YAML scenarios are re-validated as a whole after optional sections are attached, so `locked_assignments`, timeline, mobilisation, crew assignments, and `initial_state` get the same cross-checks as scenarios built in Python (#100).

### Scenario validation and compatibility (#118)
- Locks outside the block's `earliest_start`/`latest_finish` window, and locks on a block with
  `harvest_system_id` whose machine has no role or a role outside that system, are rejected (for
  YAML and Python-built scenarios alike). `initial_state.role_remaining` may not exceed the block's
  `work_required` (tolerance 1e-6 m³).
- Together with #100, `load_scenario` (and so every CLI command, including `fhops plan rolling`)
  now rejects at load: locks in blackouts, with unknown ids/shift labels or days outside the
  horizon, duplicate or mixed day/shift locks, out-of-window and incompatible-role locks,
  mobilisation distance CSVs that mention blocks outside the scenario (trim superset tables),
  crew/mobilisation entries for unknown machines, and invalid `initial_state` entries. Every
  scenario in the repository and the nine BC case-study scenarios load unchanged. Details:
  `docs/howto/data_contract.rst` ("Compatibility with FHOPS 1.0.0").
- Dependency floors raised to versions verified on Python 3.11/3.12: `pyomo>=6.9.2` (older
  releases cannot create the `highs` solver or warm-start it), `highspy>=1.8.1` (reports rejected
  MIP starts), `typer>=0.12.4` (older releases cannot build the CLI), `PyYAML>=6.0.1`.
- Source distributions no longer include an unrelated, accidentally committed `config/` directory.

### Stochastic playback (#93) — behaviour change
- Landing shocks start per landing and day and last `duration_days` calendar days (v1.0.0 sampled
  once per landing and decremented per assignment row).
- Downtime removes a sampled duration (`mean_duration_hours`, `std_duration_hours`, clipped to the
  shift length) instead of always the whole shift; downtime-hour KPIs now report sampled hours
  (they were always 0 in v1.0.0). New CLI options `--downtime-mean` / `--downtime-std`.
- Weather and landing effects compose with downtime instead of overwriting it.
- `WeatherEventConfig.correlated_days` is deprecated (it was never used; `impact_window_days`
  models multi-day spells).
- Stochastic results differ from v1.0.0 for the same seed.

### Operational MILP warm start (#99)
- `fhops solve-mip-operational --incumbent` (and `solve_operational_milp(...,
  incumbent_assignments=...)`) raised `TypeError` with HiGHS under Pyomo 6.10. Seeded HiGHS solves
  now use the APPSI HiGHS MIP start; the CLI, result, and telemetry report whether HiGHS accepted
  the start. Solvers without warm-start support fall back with `MilpWarmStartWarning`.
- Solves stopped by a time/iteration limit now return their best feasible solution (objective and
  assignments) instead of `objective=None`.

### KPIs for empty and partial plans (#108)
- `compute_kpis` reported full delivery for an empty assignment plan (e.g. a MILP run that found no
  solution). Empty plans now report 0 delivered and full remaining work; delivered + remaining
  always equals total required volume. Non-empty results are unchanged.

### MILP and playback consistency (#109, #110) — behaviour change for some scenarios
Operational-MILP plans replayed with sequencing violations under playback (≈80–120 on a 3-shift BC
case study), so playback understated MILP plans. Fixes:
- playback/heuristics release staged output per shift slot (matching E7), use one chronological
  slot order, a 1e-6 m³ tolerance, and volume-based head-starts (matching E8);
- the loader truckload rule checks volume staged at the start of the slot;
- **formulation correction**: each role's output is capped at the block's remaining volume, the
  head-start buffer is waived once upstream roles have finished the block, and the loader
  threshold is `min(truckload, remaining volume)` (v1.0.0 allowed upstream roles to process more
  wood than the block holds);
- blocks without `harvest_system_id` are unsequenced in the MILP, as in playback and the data
  contract;
- timeline blackouts are enforced in the MILP (previously only heuristics/playback).
A feasible MILP plan now replays with zero sequencing violations and playback delivers the MILP's
terminal production. Heuristic results on the SoftwareX reference ladder are byte-identical.

### Heuristics, tracker, and playback fixes (#116) — behaviour change for multi-shift scenarios
Found by the pre-release audit of the 1.0.1 candidate:
- **Multi-shift heuristic quality.** With per-shift release (#109) the SA/ILS/Tabu repair stacked
  every role of a block on its landing in the same shift, so plans on 3-shift scenarios paid more
  landing-capacity penalties than v1.0.0 (e.g. Jaffray `ka_6`, SA 1500 iterations, seeds 1–3:
  24913/23913/22913 in v1.0.0, 15913/13913/18913 in the candidate). On days with more than one
  shift the repair now keeps or fills an assignment only when the block's landing has room in that
  shift (when `landing_surplus` is weighted 0); `ka_6` now reaches 30913.36 (all volume, no
  penalty) for each seed. On capacity-limited scenarios delivered volume can be slightly lower
  because landing capacity is now respected (`pg_18`: 1–4 % less, ~600 fewer overloads).
  Single-shift results are unchanged (reference ladder byte-identical).
- **Head-start waiver** uses upstream output before the current slot (tracker and repair), as the
  MILP's `upstream_done` does; finishing the upstream role in the same slot no longer waives it.
- **`shift_id` required on multi-shift scenarios.** Playback, KPIs, stochastic playback, and
  `fhops eval-playback` raise an error when assigned rows lack `shift_id` and some day has more than
  one shift (v1.0.0 replayed them all as `S1`). Single-shift scenarios keep the `S1` default.
- **Shift hours without timeline definitions** are the machine's `daily_hours` divided by its
  number of shifts that day (shift calendar), for recorded hours, availability/utilisation, and the
  downtime fraction (v1.0.0 recorded the full `daily_hours` per shift).
- Stochastic events ignore the assignment frame's index (duplicate labels corrupted downtime and
  weather updates).
- `downtime_production_loss_est`, `weather_production_loss_est`, and `weather_hours_est` are
  record-level sums of what the events removed (v1.0.0: hours × an all-role average rate).
- Synthetic `medium`/`large` landing-shock presets recalibrated for per-landing-day shocks
  (≈4.9 % / ≈10.1 % of landing-days instead of 32.8 % / 57.8 %); the generator no longer writes
  deprecated fields to `metadata.yaml`.
- `correlated_days` and the never-used per-event `seed_offset` warn only when set to a
  non-default value; `fhops eval-playback --help` no longer drops bracketed text.

### Legacy MIP retired; `solve-mip` delegates to the operational MILP (#124, #127) — behaviour change
- **Disclosure.** The legacy day-level MIP (`fhops.optimization.mip.builder.build_model`, used by
  `fhops solve-mip`, `fhops benchmark`, and the ILS hybrid step) has been infeasible since v1.0.0
  for every scenario whose harvest system has a loader role with machines: its loader-buffer
  constraint `Σ_{≤s} prod_loader ≤ Σ_{<s} prod_prereq − batch` demands a negative buffer (−batch, e.g.
  −30 m³) in the first shift. HiGHS proves tiny7, small21, and med42 infeasible (large84 has the
  same rows); v1.0.0 `fhops solve-mip` exited with a traceback on these examples. The operational MILP
  (`fhops.model.milp`, `fhops solve-mip-operational`) — the formulation documented in the FHOPS
  paper — is not affected.
- `fhops solve-mip` is now a **deprecated alias**: it prints a one-line notice and solves the
  operational MILP. Options map to `solve-mip-operational` (`--time-limit`, `--out`, `--debug`,
  `--sequencing-debug` unchanged; `--driver auto` → Gurobi when installed, else HiGHS, with a HiGHS
  retry after a Gurobi solver error; HiGHS drivers → `--solver highs`; `gurobi` / `gurobi-appsi` /
  `gurobi-direct` → `gurobi` / `appsi_gurobi` / `gurobi_direct`). The output line
  `MIP outcome=… solver_status=… termination=… objective=…|n/a` and the exit codes (0 solver ran,
  including infeasible or no incumbent; 1 solver error or solver unavailable; 2 bad arguments) are
  kept; objectives are operational-MILP objectives.
- `fhops benchmark` solves the operational MILP for its MIP step (no deprecation notice).
- Python API: `fhops.optimization.mip.solve_mip` (deprecated, `LegacyMipDeprecationWarning`, a
  `DeprecationWarning`) delegates to the operational MILP with the same result keys (`objective`,
  `assignments`, `has_solution`, `outcome`, `solver_status`, `termination_condition`,
  `solver_error`, `warnings`; plus `production`, `warm_start`, `solver`); it never raises for
  infeasible models, time limits, or solver failures (`SolverUnavailable` only for a missing
  solver). `fhops.optimization.mip.builder.build_model` remains importable but deprecated; no
  solver uses it.
- `fhops bench suite --driver auto --include-mip` falls back to HiGHS again when Gurobi is not
  installed (since the no-raise driver change the MIP row was left empty).
- **ILS hybrid step is now a genuine warm start (#104).** `solve_ils(..., hybrid_use_mip=True)` /
  `fhops solve-ils --hybrid-use-mip` solve the operational MILP (HiGHS) with the best ILS schedule
  as a MIP start (APPSI HiGHS, same objective weights as the ILS run) and keep the MILP schedule only
  when it scores higher; a solve without a solution keeps the ILS schedule. Previously the step
  solved the legacy MIP without an incumbent, which failed on every bundled example, so it never
  changed the schedule. Results of runs with the hybrid step enabled change; the SoftwareX benchmark
  and tuning assets were generated with the hybrid step disabled and reproduce unchanged.

### Solver consistency: landing capacity, day locks, idle locked slots (#125) — behaviour change for the operational MILP
- **Landing capacity (formulation E11 correction).** The operational MILP limited the
  machine-shifts on a landing per *day* to `Landing.daily_capacity` plus a slack that was free at
  the default `landing_surplus = 0`, i.e. the capacity never bound; the heuristics (v1.0.0 and now)
  count the machines working a landing's blocks per *shift slot* and charge 1000 per extra machine
  at weight 0. The MILP now applies the heuristics' rule: per `(day, shift)` slot, hard when
  `landing_surplus = 0`, otherwise the `k`-th machine beyond capacity costs `k × landing_surplus`
  (as in the heuristics). A slot in which locks alone exceed a hard capacity keeps the locked
  machines and admits no other (warning) instead of becoming infeasible. SA and MILP plans are now
  judged by the same landing rule: MILP plans have zero landing penalties under the heuristic
  evaluation. MILP results change wherever landings bind: tiny7 (capacity-1 landings) optimum
  4388.082752 → 279.796036 (24 → 14 assignments, 12 → 0 overloads); small21 at 600 s 15645.73
  (49 overloads) → 11433.31 (0). On the 3-shift BC case-study scenarios `ka_6`/`pg_6` the MILP
  seeded with the SA plan accepts it and proves it optimal (30913.36 / 67923.96, no overloads);
  without a seed HiGHS may need much longer to find a first incumbent (`ka_6`: none within 30 min,
  where the previous model found a landing-violating optimum after ~18 min), so seed MILP runs on
  such scenarios with a heuristic plan (`--incumbent`). Heuristic incumbents that overload a landing
  are now rejected as MILP warm starts. Single-shift heuristic results are unchanged (reference
  ladder byte-identical).
- **Day-level locks on multi-shift scenarios.** A lock without `shift_id` means every shift of the
  day in which the machine is available (as in the MILP and the heuristics). Rolling-horizon
  replay/carry-forward, `compute_rolling_kpis`, and stitched-plan exports now expand such locks
  (the replay used to pass them to playback unlabelled, and replayed a day lock on a day the machine
  is unavailable as work); a day lock carrying a planned `production` on a day with several
  available shifts is rejected as ambiguous.
- **Idle locked slots.** Playback no longer reports `missing_prereq` for an assignment whose
  planned production is 0 (e.g. a locked machine the MILP keeps idle until its input is staged);
  producing without staged input is still a violation.
- `fhops evaluate` reports invalid assignment input (e.g. missing `shift_id` on multi-shift
  scenarios) as an error message with exit status 1 instead of a traceback.

### Documentation (#94, #95)
- `Block.work_required` documented consistently as terminal delivered volume in m³.
- SoftwareX playback figure redrawn for legibility; playback assets regenerated with the fixed

## Migration Notes
- Upgrade with `pip install --upgrade fhops==1.0.1`. Scenario schema version stays `1.0.0`; all
  new fields are optional.
- Re-run any rolling-horizon studies, stochastic-playback analyses, and MILP results evaluated with
  playback that were produced with v1.0.0.
- If you passed `correlated_days` or `seed_offset` explicitly, remove them (they had no effect).
- Run `fhops validate` on your scenarios: inputs listed under "Scenario validation and
  compatibility" now fail at load. Pin `fhops>=1.0.1` in projects whose scenario files use
  `initial_state` or lock `shift_id`.
- Provide `shift_id` in assignment CSVs for scenarios with more than one shift per day.
- Re-run heuristic (SA/ILS/Tabu) studies on multi-shift scenarios produced with v1.0.0 or a 1.0.1
  pre-release.
- Replace `fhops solve-mip` with `fhops solve-mip-operational` and
  `fhops.optimization.mip.solve_mip` with `fhops.model.milp.driver.solve_operational_milp`; the
  deprecated entry points will be removed in a future release. Legacy `solve-mip` objectives from
  v1.0.0 (where it ran at all) are not comparable with operational-MILP objectives.
- Re-run operational-MILP studies whose landings can bind (`landing_surplus = 0` and fewer
  landing slots than machines): the MILP now enforces landing capacity per shift slot (#125).
