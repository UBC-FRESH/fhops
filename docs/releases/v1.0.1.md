# FHOPS v1.0.1

## Summary
- Maintenance release on the stable 1.0 line (Phase 8, parent issue #90), cut from `v1.0.0`.
- Fixes defects found during the SoftwareX R2 review of the FHOPS manuscript
  (UBC-FRESH/fhops-manuscript#20): rolling-horizon state carry-forward, stochastic playback
  event semantics, MILP warm start with HiGHS, and lock validation.
- Adds one optional, backward-compatible scenario-contract section (`Scenario.initial_state`) and an
  optional `ScheduleLock.shift_id`. Scenarios without them behave exactly as in v1.0.0
  (regression-tested on reference scenarios for SA, the operational MILP, and playback).
- The tactical–operational planning layer remains on the separate 1.1.0 alpha line
  (`pip install --pre fhops==1.1.0a1`) and is not part of this release.

## Installation

pip install fhops==1.0.1

## Fixes and changes

### Rolling-horizon planning (#92) — behaviour change
In v1.0.0 the rolling-horizon driver (`fhops plan rolling`, `fhops.planning.solve_rolling_plan`)
carried no state between windows, contrary to its design notes:
- every window re-planned each block's full `work_required`, including blocks finished in earlier
  locked days;
- staged inter-role inventory, role progress, and head-start counts restarted at zero;
- machines had no starting position, so moves at window boundaries were free inside the solve;
- user `Scenario.locked_assignments` were dropped;
- blackout timelines were not rebased into window coordinates;
- locks lost their `shift_id`.

v1.0.1 replays the stitched locked plan after each window against the base scenario (the same
sequencing-tracker path playback uses) and carries the resulting state into the next window:
remaining block volume (`work_required`; finished blocks stay at 0), per-role remaining output,
staged inventory and shift counts, and each machine's last block (`Scenario.initial_state`). User
locks are merged into every window, blackouts are rebased into window coordinates, locks keep
`shift_id`, and MILP locks carry the production the MILP planned so the replay executes the plan
the solver chose. Stitched-plan KPIs (`compute_rolling_kpis`) use the same replay, so carried
state and reported KPIs agree. Hooks record runtime; `solver="auto"` resolves to HiGHS.
**Rolling-horizon results from v1.0.0 and earlier should be re-run.** Known limitation: windows
assign no value to work-in-progress left at the window end, so very short windows relative to the
harvest-system chain can under-plan upstream work.

### Scenario contract (#91)
- New optional `Scenario.initial_state` (`BlockInitialState`: `role_remaining`, `staged_inventory`,
  `role_shift_counts`; `MachineInitialState`: `last_block_id`), honoured by the operational MILP
  (first-slot staged inventory and head-start, per-role remaining cap, boundary move cost), the
  heuristics, and playback.
- New optional `ScheduleLock.shift_id` (`None` = whole day). The operational MILP now enforces
  `Scenario.locked_assignments` (previously ignored by that builder).
- YAML scenarios are re-validated as a whole after optional sections are attached, so `locked_assignments`, timeline, mobilisation, crew assignments, and `initial_state` get the same cross-checks as scenarios built in Python (#100).

### Stochastic playback (#93) — behaviour change
- Landing shocks start per landing and day and last `duration_days` calendar days (v1.0.0 sampled
  once per landing and decremented per assignment row).
- Downtime removes a sampled duration (`mean_duration_hours`, `std_duration_hours`, clipped to the
  shift length) instead of always the whole shift; downtime-hour KPIs now report sampled hours
  (they were always 0 in v1.0.0). New CLI options `--downtime-mean` / `--downtime-std`.
- Weather and landing effects compose with downtime instead of overwriting it.
- `WeatherEventConfig.correlated_days` is deprecated (it was never used; `impact_window_days`
  models multi-day spells).
- Stochastic results differ from v1.0.0 for the same seed.

### Operational MILP warm start (#99)
- `fhops solve-mip-operational --incumbent` (and `solve_operational_milp(...,
  incumbent_assignments=...)`) raised `TypeError` with HiGHS under Pyomo 6.10. Seeded HiGHS solves
  now use the APPSI HiGHS MIP start; the CLI, result, and telemetry report whether HiGHS accepted
  the start. Solvers without warm-start support fall back with `MilpWarmStartWarning`.
- Solves stopped by a time/iteration limit now return their best feasible solution (objective and
  assignments) instead of `objective=None`.

### KPIs for empty and partial plans (#108)
- `compute_kpis` reported full delivery for an empty assignment plan (e.g. a MILP run that found no
  solution). Empty plans now report 0 delivered and full remaining work; delivered + remaining
  always equals total required volume. Non-empty results are unchanged.

### MILP and playback consistency (#109, #110) — behaviour change for some scenarios
Operational-MILP plans replayed with sequencing violations under playback (≈80–120 on a 3-shift BC
case study), so playback understated MILP plans. Fixes:
- playback/heuristics release staged output per shift slot (matching E7), use one chronological
  slot order, a 1e-6 m³ tolerance, and volume-based head-starts (matching E8);
- the loader truckload rule checks volume staged at the start of the slot;
- **formulation correction**: each role's output is capped at the block's remaining volume, the
  head-start buffer is waived once upstream roles have finished the block, and the loader
  threshold is `min(truckload, remaining volume)` (v1.0.0 allowed upstream roles to process more
  wood than the block holds);
- blocks without `harvest_system_id` are unsequenced in the MILP, as in playback and the data
  contract;
- timeline blackouts are enforced in the MILP (previously only heuristics/playback).
A feasible MILP plan now replays with zero sequencing violations and playback delivers the MILP's
terminal production. Heuristic results on the SoftwareX reference ladder are byte-identical.

### Heuristics, tracker, and playback fixes (#116) — behaviour change for multi-shift scenarios
Found by the pre-release audit of the 1.0.1 candidate:
- **Multi-shift heuristic quality.** With per-shift release (#109) the SA/ILS/Tabu repair stacked
  every role of a block on its landing in the same shift, so plans on 3-shift scenarios paid more
  landing-capacity penalties than v1.0.0 (e.g. Jaffray `ka_6`, SA 1500 iterations, seeds 1–3:
  24913/23913/22913 in v1.0.0, 15913/13913/18913 in the candidate). On days with more than one
  shift the repair now keeps or fills an assignment only when the block's landing has room in that
  shift (when `landing_surplus` is weighted 0); `ka_6` now reaches 30913.36 (all volume, no
  penalty) for each seed. Single-shift results are unchanged (reference ladder byte-identical).
- **Head-start waiver** uses upstream output before the current slot (tracker and repair), as the
  MILP's `upstream_done` does; finishing the upstream role in the same slot no longer waives it.
- **`shift_id` required on multi-shift scenarios.** Playback, KPIs, stochastic playback, and
  `fhops eval-playback` raise an error when assigned rows lack `shift_id` and some day has more than
  one shift (v1.0.0 replayed them all as `S1`). Single-shift scenarios keep the `S1` default.
- **Shift hours without timeline definitions** are the machine's `daily_hours` divided by its
  number of shifts that day (shift calendar), for recorded hours, availability/utilisation, and the
  downtime fraction (v1.0.0 recorded the full `daily_hours` per shift).
- Stochastic events ignore the assignment frame's index (duplicate labels corrupted downtime and
  weather updates).
- `downtime_production_loss_est`, `weather_production_loss_est`, and `weather_hours_est` are
  record-level sums of what the events removed (v1.0.0: hours × an all-role average rate).
- Synthetic `medium`/`large` landing-shock presets recalibrated for per-landing-day shocks
  (≈4.9 % / ≈10.1 % of landing-days instead of 32.8 % / 57.8 %); the generator no longer writes
  deprecated fields to `metadata.yaml`.
- `correlated_days` and the never-used per-event `seed_offset` warn only when set to a
  non-default value; `fhops eval-playback --help` no longer drops bracketed text.

### Documentation (#94, #95)
- `Block.work_required` documented consistently as terminal delivered volume in m³.
- SoftwareX playback figure redrawn for legibility; playback assets regenerated with the fixed
  events (deterministic benchmark, tuning, and scaling assets re-verified unchanged).

## Migration Notes
- Upgrade with `pip install --upgrade fhops==1.0.1`. Scenario schema version stays `1.0.0`; all
  new fields are optional.
- Re-run any rolling-horizon studies, stochastic-playback analyses, and MILP results evaluated with
  playback that were produced with v1.0.0.
- If you passed `correlated_days` or `seed_offset` explicitly, remove them (they had no effect).
- Provide `shift_id` in assignment CSVs for scenarios with more than one shift per day.
- Re-run heuristic (SA/ILS/Tabu) studies on multi-shift scenarios produced with v1.0.0 or a 1.0.1
  pre-release.
